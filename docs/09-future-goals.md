## 1. G1 账号体系（登录 / 角色 / 权限）

### 1.1 现状

- 全站**无用户体系**：`README §4.2` 明确「本期不做用户体系与登录鉴权」，看板四个页面只读、无鉴权。
- 唯一例外是身份匹配控制台的写接口 `/api/identity/*`：使用**单一管理员令牌** `ADMIN_TOKEN`（`X-Admin-Token` 请求头，守卫为 `AdminTokenGuard`，见 `04 §5.3.14`），令牌由使用者自己在浏览器标签页内配置、不落盘（`02 §14`）。`04 §5.1` 的鉴权约定原文是「**仅写接口**需要 `X-Admin-Token`，读接口不鉴权；未配置 `ADMIN_TOKEN` 时所有写接口整体禁用并返回 `40301`」。
- 部署形态是**局域网同域反代**（`08`）：同网段任何机器都能打开看板；令牌一旦泄露即等同全量写权限，且**无法区分是谁在改**。
- 审计流水 `data/.identity-audit.jsonl` 明确为**非契约**、只追加、不参与前端展示（`04 §5.3.14`），因此既记不到自然人操作者，也没有查询入口。

### 1.2 目标

1. **有登录账号**：至少区分「未登录访客 / 已登录用户 / 管理员」三态。
2. **有角色与权限**：写接口从「持令牌即可」改为「按角色授权」；操作者身份写入审计流水，使「谁在什么时候改了什么」可追溯。
3. **支撑 G2**：视角可见性由账号角色决定，而不是靠 URL 约定或前端隐藏。
4. **迁移路径明确**：`ADMIN_TOKEN` 保留为应急后门还是彻底退役，须在开工前裁定（§1.3 Q5）——运营已在用它维护认领关系，不能出现「升级当天没人能改数据」。

## 2. G2 社区 / 星火部内部双视角呈现

### 2.1 目标与动机

同一份采集数据要服务两类完全不同的读者：

- **社区视角（对外）**：面向 OpenAN 社区与成员单位，回答「社区整体在往哪走、各单位贡献如何」。倾向**组织级聚合**、正向呈现、可公开。
- **星火部内部视角（对内）**：面向本部门运营与管理，回答「我们自己人做了什么、哪里没做到位、下一步该催谁」。倾向**个人级明细**，并且要看得见缺口——未认领账号、未归属贡献、解析失败的联系人、采集健康度。

**动机**：当前看板只有一个视角（≈对外口径），内部运营要的明细与缺口只能靠直接读 `data/*.json` 和采集日志，效率低且容易口径走偏；反过来，把内部明细直接摊在对外看板上又有泄露与观感风险。因此需要**同源数据、两套呈现**——注意是「两套呈现」而非「两套口径」：同一指标在两个视角下应当同值（见 §2.4 Q5）。

### 2.2 现状盘点：哪些内容天然偏「对内」

| 现有资产 | 当前可见性 | 备注 |
| --- | --- | --- |
| 组织级聚合（首页指标、组织墙、活跃度组织明细、环形图） | 已对外呈现 | 社区视角的主体，基本不用动 |
| 个人贡献排行（GitHub 前 8） | 已对外呈现 | 是否继续对外，待裁定（§2.4 Q2） |
| 例会参会矩阵（人 × 日期、出席率） | 已对外呈现 | 含**个人出席率**，敏感度最高，Q2 重点 |
| 独立开发者（`orgId=null`）明细 | 已对外呈现 | 未认领者的贡献以独立开发者身份出现 |
| 身份匹配控制台 `/admin/identity` | 页面可开、写操作需令牌 | 典型对内工具 |
| 候选池 / 未归属账号 / 解析失败的联系人 | 部分在控制台内，部分只在 `data/.sync-state.*.json` 与采集日志 | **对内缺口清单尚未成为页面**；`06` §1（当前唯一开放项）：12 条组织档案的 `aliases.github` / `aliases.confluence` 全为空 |
| 采集健康度与运维信号（限流退避、增量水位、`partnerCount` 10 vs 11 这类不一致） | 仅日志 / 文件 | 对内运维视角；相关待办见 `07 §4`（P1 补别名、A3 Confluence 归属回归、A9 GitHub 归属收敛、P4 未归属补录、P6 自动匹配建议） |
| 环比趋势（`delta` / `deltaDirection` 现为运营手工值） | 手工维护 | `07 §2.1` 已把「基于历史快照算环比」列为待补项，并附带**硬约束**：快照中存在已退休枚举，环比代码不得用 `isOrganizationArray` 校验历史快照 |

### 2.3 三条可选路线（提案，未定稿）

| 路线 | 做法 | 优点 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 同一站点、按角色渲染** | 一套前端，按登录角色决定区块与页面可见性 | 复用组件与接口，维护成本最低 | 前端隐藏**不等于**访问控制；必须配合服务端裁剪，否则数据仍在响应体里 |
| **B. 接口分视角** | 后端按视角出两套 DTO，或统一加 `?view=community\|internal` 查询参数 | 访问控制在服务端；两个视角的呈现可分别演进 | 接口面翻倍，`04 §5` 几乎每条都要标注视角，契约需系统化重构 |
| **C. 两个独立站点** | 对外站 + 内网站分开构建、分开部署 | 隔离彻底；对外站可放公网 | 两套构建与部署，`08` 的部署形态要重做；产物与缓存需分别管理 |

**当前倾向**：**A + B 组合**（前端按角色渲染，服务端按视角裁剪字段与明细），前提是 G1 先落地。**C** 只在「对外要上公网」时才考虑——届时还要回答公网带来的鉴权、限流与合规问题，已超出 `08` 局域网指南的范围。

### 2.5 与既有决策的关系

- **不改任何现有指标口径**：`04` 仍是唯一契约来源；视角只决定**呈现哪些字段**，不决定**字段怎么算**（§2.4 Q5）。
- **组织级 / 个人级双粒度**（`ADR-0008`）天然适配双视角：组织级→对外、个人级→对内。但这**不是**一一映射（对外也有个人排行、对内也要看组织汇总），最终以 Q2 的逐项裁定为准。
- **读时派生**（`ADR-0010`：认领覆盖 + 派生生效字段）为「按视角裁剪」提供了实现基础——裁剪发生在派生**之后**，不新增派生规则。
- **历史快照**（`07 §2` P4：`data/.snapshots/`，保留最近 7 份用于回滚）与视角正交：快照是「数据随时间」的留痕，视角是「数据按受众」的裁剪，两者不要混用。
