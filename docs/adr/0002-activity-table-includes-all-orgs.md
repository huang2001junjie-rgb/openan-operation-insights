# ADR-0002：社区活跃度明细表纳入全部组织

- **状态**：已接受
- **日期**：2026-09-21
- **关联文档**：02 §4.1/4.2、README §5 术语表；演进自 ADR-0001

## 背景

活跃度页"组织贡献明细"表的行数据由前端将 `GET /api/contributions` 与 `GET /api/wiki` 两份响应按 `orgId` 合并而成，组织档案（`organizations.json`）不参与。贡献数据尚未接入完整（GitHub 采集仅产出 `unattributed` 一条，Confluence 孤儿记录已随 ADR-0001 清理），明细表因此只剩一行"独立开发者"，其余 10 个组织在页面不可见。

ADR-0001 已让首页组织墙展示社区全貌，活跃度明细表由此成为最后一个"只有有贡献的组织才可见"的视图。

## 决策

经评审拷问，确定以下三点：

1. **合并层级**：全量补零在**前端合并层**实现——`mergeActivityRows` 增加组织档案入参，以档案为底表连接两份贡献数据。后端 `/contributions`、`/wiki` 契约不动，保持"有记录才返回"的诚实语义。
2. **展示规则**：档案中每个组织各占一行，无贡献记录的指标按 0 展示、更新时间与仓库数显示"—"；名称 / Logo / 官网以**档案为准**（档案是展示基准），贡献记录仅提供指标数值。`orgIds` 筛选同时作用于档案底表，选中无贡献组织时该组织以全 0 行呈现。
3. **降级与兜底**：组织档案接口失败时退回两源合并的旧行为（只有贡献记录行），不阻塞页面、不报错；贡献记录中 `orgId` 不在档案内的行照旧保留，避免数据漂移被静默吞掉。

**排行榜不受影响**：`ContributionRankCard` 既有逻辑已按当前指标过滤 `> 0` 再取 Top 8，零值组织天然不进入图表，无需改动。

## 理由与取舍

| 选项 | 结论 |
| --- | --- |
| 补零层级：前端 merge / 后端接口 | **前端 merge**。明细表合并逻辑本就在前端，扩展一个入参即可；后端拼需同时改造 `/contributions` 与 `/wiki` 两个接口，且"贡献接口返回无贡献组织"与 ADR-0001 中 `scope=contributing` 名不符实是同类坑 |
| 排行榜零值处理：沿用 `> 0` 过滤 / 照画空条 | **沿用既有过滤**。组件已实现，图表语义（排名榜上无成绩不出现）直觉正确 |
| 档案与记录字段冲突：档案优先 / 记录优先 | **档案优先**。档案是人工维护的展示基准，贡献记录只负责指标数值 |

## 后果

- **正面**：明细表呈现社区全貌（全量档案行数）；筛选单个无贡献组织时以全 0 行呈现（此前为空表）；与首页组织墙口径一致。
- **负面**：`rows` 的数据源从 2 份变 3 份，`ActivityPage` 加载态组合新增档案依赖；组织档案接口成为明细表的隐性依赖（失败时静默降级，行数变少但不报错）。
- **不受影响**：贡献类型分布环形图（`/contributions/summary`）、排行榜（内部 `> 0` 过滤）、后端全部接口契约、组织筛选下拉（本就取全量档案）。
- **对 ADR-0001 的修订**：其"不受影响"清单中"社区活跃度页"一条随本决策失效。
