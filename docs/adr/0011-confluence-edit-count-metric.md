# ADR-0011：Confluence「编辑量」指标（页面版本作者计数）

- **状态**：✅ 已接受（2026-09-29）
- **日期**：2026-09-29
- **关联文档**：04 §3.11 / §4.10 / §5.3.4 / §5.3.16；08 §1.2（A3 / A7）/ §3.2.1；02 §4.1；ADR-0001（贡献分公式与阈值）/ ADR-0008 / ADR-0009 / ADR-0010
- **决策者**：项目负责人（编辑量口径三问 + 接入方式两问逐条拍板）

## 背景

Confluence 维度原有**两个**成果数量指标：`requirements`（需求）与 `topicShares`（议题分享）。两者都只统计**结构选择器命中页**（需求页 / 会议纪要页）里**正文 @ 提及**的账号，属于"被点名"的次数，反映的是**协作关系**而非**编辑产出**——空间里存在大量没有 @ 任何人的编辑工作（页面搭建、内容更新、结构调整），当前口径完全看不到。

本轮希望补一个与两者**并列**的第三个成果数量指标「编辑量（`edits`）」，回答"谁在这个空间里真正动手写了内容"。

事实核查（2026-09-29 对真实空间 `OpenAN` 只读实测）：

1. Confluence Cloud 提供官方 **v2 版本接口** `GET /wiki/api/v2/pages/{id}/versions`，逐条返回 `number`（版本号）、`authorId`（作者账号，**版本作者的唯一真相**）、`createdAt`、`message`、`minorEdit`。空间 53 页共 **672 个版本**、**19 位作者**。
2. 版本接口**只回 `authorId`、不回展示名**；而 v1 `/rest/api/user` 对采集令牌返回 **403**、v2 用户路由不可用。**唯一有效的展示名来源**仍是正文渲染视图 `body.view`（与 ADR-0009 相同通路）。
3. 空间存在极端集中页：`Requirement Proposal` 单页 **146 个版本**（约占全空间 22%）；前三位作者合计约占 76%。若按"版本数"直接排行，会把"编辑密集页"误读为"个人产出"。

三个口径问题由决策者拍板：**① 不修正异常集中页；② 展示名用渲染视图补全；③ 保留页面创建那一次（版本号从 1 起算，不做扣减）**，并把编辑量作为 requirements / topicShares 之外**并列的第三个数量**。

## 决策

| # | 问题 | 决策 |
| --- | --- | --- |
| 1 | 计数单位 | **页面版本条数**：逐版本归属到该版本的 `authorId`，每个版本计 1 次 |
| 2 | 创建版本 | **包含**：页面创建即版本 `number = 1`，原样计入，**不扣减**（"动过一次手"即算一次编辑） |
| 3 | 统计范围 | **空间内全部页面**（非仅需求页 / 纪要页）——实测 53 页 |
| 4 | 异常集中页 | **不修正**：`Requirement Proposal` 的 146 个版本原样计入，不做封顶、剔除或加权 |
| 5 | 展示名 | **复用渲染视图 `body.view`**（`extractRenderedUserNames`），不新增解析逻辑、不依赖 `/rest/api/user` |
| 6 | 组织归属 | **完全复用既有解析链**：认领边（读时，ADR-0010）→ `aliases.confluence` → 空间兜底 → 伪组织 `unattributed` |
| 7 | 贡献分 | **计入**：`computeScore = PR + issues + requirements + topicShares + edits + linesChanged/10000`；**阈值重校** `300/100 → 600/100`（依据见下） |
| 8 | 展示露出 | **四处**：组织成果明细表新增「编辑」列、个人成果排行卡新增「编辑」口径、成果分布环形图支持按编辑量拆分、活动总表新增「编辑」列 |

### 取数（决策 1～4）

- 新增 `ConfluenceSource.fetchPageVersions(pageIds)`：逐页 `GET /wiki/api/v2/pages/{id}/versions?limit=200`，用 `_links.next` 游标翻页（实测最大单页 146 个版本，200 已够，但仍实现翻页以防将来超限）。
- **不传 `sort`**：v2 版本接口的 `sort` 只接受 `modified-date` / `-modified-date`，传 `number` 会 `400 Invalid sort order`（实测踩到）；编辑量只按条数计、与顺序无关，故取默认序并在客户端自行按 `number` 升序归一。
- 失败降级：单页失败**只把该页编辑量按 0 计**并记警告，不中断整轮；与 `fetchPageBodies` 的容错风格一致，**不影响** requirements / topicShares 与既有落盘。

### 补名（决策 5，关键设计）

版本接口不给展示名，而正文是**按需拉取**的，因此必须先回答"谁还没名字"，才能只对差集页补正文：

1. 先取**全量页面版本**，算出 `authorId → 编辑次数` 与 `authorId → 涉及的空间集合`。
2. 汇总"零成本即可得名"的账号：页面事实里的**创建者 / 最后修改者**展示名。
3. 对仍未命名的版本作者，收集其编辑过的页面，**与既有正文目标页（需求页 + 纪要页）做差集**后并入 `fetchPageBodies`，复用现成的 `extractRenderedUserNames` 换名。
4. 实测差集仅 **18 页**，本轮渲染视图共换出 **24 个账号展示名**，19 位版本作者**全部补出真名**（100%）。

顺序上必须**先版本、后补名差集**（否则会漏掉只在非需求 / 纪要页出现的作者）。

### 聚合与归属（决策 6）

- `AccountGroup` 增加 `edits`；版本作者走与 @ 提及账号**完全相同**的归属解析链。
- 编辑量累加时**同时**把"该账号编辑过的页面的 `spaceKey`"并入其 `spaces` 集合：否则依赖"全部计数落在同一被认领空间"的**空间兜底**判定会退化，把本可归属的账号误判进伪组织。

### 贡献分与阈值重校（决策 7）

编辑量与 PR / Issue / 需求 / 议题分享同属"行为频次"，直接计入；代码量仍按万行折算。由于编辑量量级（数百）显著高于既有行为指标，**必须**重校分档阈值，否则分档会失真。

实测**含编辑量**的组织贡献分分布（`OpenAN`，11 个组织）：

| 组织 | 分 | 旧档（300/100） | 新档（600/100） |
| --- | --- | --- | --- |
| Huawei | 802 | 高 | **高** |
| 独立开发者（`unattributed`） | 527 | **高** | **中** |
| China Mobile | 45 | 低 | 低 |
| ZTE | 1 | 低 | 低 |
| 其余 7 个 | 0 | 低 | 低 |

非零分 **`[1, 45, 527, 802]`**，`p75 ≈ 527`、`p50 ≈ 45`。据此取 **`HIGH = 600` / `MEDIUM = 100`**：

- 只有体量明显领先的华为为**高贡献**；聚合了大量个人编辑的「独立开发者」桶落**中档**（旧阈值下它会被一起推入最高档，把"高产个人汇聚的桶"误读为组织级最高贡献）；
- 移动（45）及以下仍为**低档**——与引入编辑量前的分档成员（ADR-0001）**完全一致**，仅是随新量级整体上调，保证金字塔形态不因新指标而坍缩为"全员最高档"或"中档真空"。

## 理由与取舍

- **为什么用 v2 版本接口**：它是官方文档中的稳定端点，`authorId` 是版本作者的**唯一真相**；v1 只能拿到"当前版本作者"（空间 53 页 → 53 个数），无法还原历史编辑量。
- **为什么含创建版本**：创建页面本身就是一次内容产出；扣减会让"新建页面的人"少算一次，与"谁动手写了内容"的意图相悖。
- **为什么不修正异常集中页**：`Requirement Proposal` 是需求汇总页，多人反复维护是**真实工作量**；封顶/剔除需要主观定阈值，会引入不可解释的偏差。代价是集中度偏高（单页约占全空间 22%、前三位作者合计约 76%），因此**必须在采集日志、指标悬停说明与本 ADR 中如实标注集中度**，避免误读。
- **为什么补名复用渲染视图而非 `/rest/api/user`**：后者对采集令牌 403、v2 用户路由不可用，实测**只有**渲染视图能稳定给出真名；且正文本就为需求 / 纪要口径拉取，差集复用不新增解析逻辑。
- **为什么只对差集页补正文**：全量拉正文会把请求从"十几页"抬到"53 页"；差集实测仅 18 页，成本可控。
- **为什么编辑量走读时派生**：与 ADR-0010 一致——组织级 = 账号级按生效归属求和，认领边命中即生效，无需重跑采集。

## 后果

### 受影响面（契约变更，破坏性）

- **`ConfluenceMetrics` 新增必填 `edits: number`**；`ContributionTotals` 同步新增 `edits`。
- **数据版本**：组织级 `confluence-organizations.json` `schemaVersion` **2 → 3**；账号级 `confluence-accounts.json` `schemaVersion` **3 → 4**（字段新增即不兼容变更，fail-fast 校验器同步收紧）。
- **投影**：`deriveOrganizationWiki` 求和带上 `confluence.edits`；`activity` 汇总、身份候选池 `metrics` 同步带上 `edits`。
- **采集器**：`run()` 接入版本取数 + 补名差集；`parseContent` 聚合版本作者；快照 `derived` 增加 `pageEdits`（被编辑页 + 编者），供离线核对口径。
- **前端**：明细表新增「编辑」列（可排序、含合计行）、排行卡新增「编辑」口径、构成环形图支持按编辑量拆分、活动总表新增「编辑」列。

### 请求成本

- 版本接口 **53 次**（每页 1 次）+ 补名差集 ≈ **18 次** ≈ **每轮 +71 次**；页数增长时线性增长，受 `REQUEST_SPACING_MS` 节流保护，不会对 Confluence 造成突发压力。
- 复杂度 `O(页面数 + 版本总数)`，无嵌套遍历、无重复请求。

### 不变

- 需求数与议题分享的**计算逻辑、选页规则完全不动**，只做叠加（仍是 ADR-0009 口径）。
- 展示名只影响可读性，**不参与计数与归属**；取不到时降级显示账号 ID。
- `confluence-organizations.json` 仍是**基线快照**（非读路径来源，ADR-0010）。

### 回归风险点（登记）

1. 契约新增必填字段会让旧数据文件校验失败——必须与 `schemaVersion` 升版、**重跑采集**一并处理（已完成）。
2. 阈值不重校会造成分档失真——已按实测分布重校为 600/100。
3. 单页版本数若超过 `limit` 且未翻页会**静默少算**编辑量——已实现游标翻页并设翻页上限告警。

## 验证

重跑采集（2026-09-29）实测：

- `版本历史：53/53 页共 672 个版本（19 位作者）` → 编辑量合计 **672**，与只读实测一致；
- 补名：渲染视图换出 **24** 个展示名，**19 位版本作者全部为真名**（100%）；
- 请求数 **74**（页面列举 + 正文 + 版本），组织级投影按生效归属求和后 `编辑 = 672`；
- `HTTP 请求`、`需求 38`、`议题分享 20` 与既有口径一致（未受影响）。
