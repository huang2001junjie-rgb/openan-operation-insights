# ADR-0009：Confluence 两个维度改为「结构选页 + 正文按人计数」，`bestPractices` 替换为 `topicShares`

- **状态**：已接受
- **日期**：2026-09-28
- **关联文档**：05 §3 / §5.3、04 §3.3、08 A3；**取代** ADR-0007 的决策 1（判定口径）与决策 5（`bestPractices` 恒 0）；与 ADR-0008（双粒度）叠加，不改其结论
- **影响面**：口径解析、采集源（新增按页取正文）、契约字段、`schemaVersion`、前端一列与贡献分公式

## 背景

ADR-0007 定的是**页面级启发式**：`标题关键字 requirement` 命中即算 1 条需求，`bestPractices` 恒 0。它解决了"从 0 到 1"，但把每张 `Requirement Proposal` 页只算成 **1 条需求**，而真实正文里：

- 需求页里的**需求是一条表格行**（29 行），联系人写在 `Contacts` 列，且 **10/29 行有两个联系人**；
- 真正与人相关的量是**提及数**（38 处）而不是页面数（2 页）；
- 会议纪要页里存在第二个可统计的维度：`Agenda` 段是「议题标题 + @分享人」的段落流（24 处 @；
  分享人写在**段落**里，该段唯一那张布局表格的行内没有 @ —— 这处细节在首次真实采集后被修正，见「后续修订」），
  而同页 `Attendees & Representation` 段的 125 处 @ 是**出席签到**（占全页 156 处的 80%）。

也就是说：09-28 的只读实测把口径的**计数单位**问题摆了出来 —— 页面不是"需求"，`Contacts` 单元格里的账号才是；而"最佳实践"这个维度在 wiki 里根本不存在，真正存在的是"议题分享"。

同时用户明确确认：**`best-practices` 不在 Confluence wiki 内**，`bestPractices` 不应由本来源产出。

## 决策

1. **需求 requirements = 结构选页 → 表格列取人**
   选页：`title == Requirement Proposal` 且 `ancestorTitles` 含 `Release Planning`（排除 `Releases` 下同名模板页）。
   取数：该页**唯一表格**的 `Contacts` 列，**每个 @ 提及各算 1 条**（一行两位联系人则两位各得 1 条）。
   **只取该单元格**：表格外另有约 33 处 @（`Status` 等列），不能计入。

2. **议题分享 topicShares = 段内取人，按期去重**（取数范围经「后续修订」放宽为段内全部 @）
   选页：标题匹配 `^\d{4}-\d{2}-\d{2} TSC Minutes$` **且直接父页**匹配 `^\d{4} - TSC Minutes$`。
   取数：`Agenda` 段**内**的全部 @（段落里的与表格行里的都算），**同一期同一账号最多算 1 次**
   （≈ 参加了几期会议的议题分享）。
   不取该页其它位置的 @：出席签到段占 80%，取错得到的是"出席次数"。

3. **`bestPractices` → `topicShares`**：`ConfluenceMetrics` 与 `ContributionsTotals` 的第二维改名，
   wiki 恰为 `{ requirements, topicShares }`；贡献分公式、前端列名（「最佳实践」→「议题分享」）、
   排序枚举 `sortBy` 同步替换。

4. **`schemaVersion` 1 → 2**（`confluence-organizations.json`、`confluence-accounts.json`）：
   字段改名是不兼容变更，读侧必须 fail-fast，不能静默把 `topicShares` 读成 `undefined` 而悄悄按 0 处理。

5. **采集源新增「按页取正文」**：`ConfluenceSource.fetchPageBodies(pageIds)`。
   只对选择器命中的目标页调用（量级十几页），**不做全空间正文展开** ——
   正文体积远大于元数据，全量展开是纯浪费且放大限流风险。

6. **计数单位从「页」改为「账号 × 维度」**：`requirements` / `topicShares` 都是**计数**，
   组织级仍是**求和派生**（ADR-0008 的双粒度不变，账号级只是多了一个维度）。

7. **解析不出账号的纯文本 `@人` 不猜、不丢**：写入状态文件 `unresolvedContacts`
   （`source` 区分 `requirements` / `minutes`，带页 + 行号 + 需求标题 + handle 原文），
   运营把正文改成真正的提及后重跑。首次真实采集共 3 处（需求行 1 处、纪要 `Agenda` 段 2 处）。

8. **展示名只影响可读性**：原先设计为三级兜底（正文 `ri:username` → 页面创建者展示名 →
   `GET /rest/api/user`），全失败则显示 accountId。**任何一条都不参与计数与归属**，
   因此查询失败只降级、不报错。实测（见「后续修订之二」）：正文里**没有** `ri:username` 这个属性、
   `/rest/api/user` 返回 403，但**渲染视图 `body.view` 已带出展示名** —— 故实际兜底顺序
   改为「渲染视图 → 正文 `ri:username` → 创建者展示名 → `/rest/api/user` → accountId」，
   首采 15 个账号全部取到真名。

## 理由与取舍

| 选项 | 结论 |
| --- | --- |
| 计数单位：页 / 行 / 人 | **人（提及）**。页数与人无关（2 页 vs 38 处提及），行数会把"共同承接"抹掉 |
| 多联系人：只算第一个 / 平均 / 每人各 1 条 | **每人各 1 条**。共同承接是事实，认可双方；代价是总数大于行数（38 > 29），已在文档注明 |
| 第二个维度：留 `bestPractices` 恒 0 / 换 `topicShares` | **换**。字段恒 0 会被读成"漏采"，而 Agenda 段的分享人是真实可得且与人相关的量 |
| 议题分享范围：全页 @ / Agenda 段全部 @ / Agenda 段**表格行** | **段内全部 @**（**已修订**，见「后续修订」）。全页会把出席签到算成分享（156 vs 24）；限定表格行则实测**恒 0** —— 该段只有一张布局表格，分享人写在段落里 |
| 计数语义：原始次数 / 按期去重 | **按期去重**。"参加了几期会议"比分不出期的重复 @ 更可解释 |
| 选页信号：标签 / 标题关键字 / 结构（标题 + 祖先链） | **结构**。空间无任何需求标签；关键字会把模板页算进来 |
| 父页匹配：字面量 / 正则 | **正则**。年份会滚动，写死 `2026 - TSC Minutes` 会在跨年后静默取到 0 |
| 取不到正文的页：整轮失败 / 跳过 | **跳过并告警**，单页异常不中断整轮（但全页无 Agenda 段会判为口径失配而中止） |

## 后果

**正面**

- 需求数与议题分享次数都变成"人"的可解释计数，与 GitHub 维度共享同一套「人 → 组织」档案。
- 口径全部收敛在**纯函数解析器**（`confluence-content.parser.ts`）里，可用固定样例离线回归
  （`npm run collect:wiki:check` 70 项断言覆盖选页、两个口径、四条归属路径、展示名兜底顺序、幂等与兜底）。
- 收紧了 ADR-0007 已知的启发式缺陷：同名模板页被祖先链条件排除，不再是误计风险。

**负面（明知并接受的负债）**

- **口径依赖正文结构**：表头列名、段名、层级一旦改版即解析不到。故全部做成「留空取默认」的环境变量，
  并保留三条自检信号（选到 0 页 / 全部会议页无 Agenda 段 / 有 Agenda 段却 0 个分享人，即中止写入）。
- **需求条数 ≠ 表格行数**（38 vs 29），对外解释时必须说明"每个联系人各 1 条"。
- **归属当前仍几乎全空**：`aliases.confluence` 与 `source=confluence` 的认领边都是空的，
  首次真实采集会把两个维度全部记到「独立开发者」。这是"数据尚未补"而非缺陷，
  账号级清单与 `unattributedAccounts` 已给出待办。
- **换口径需要重新取正文**：快照只落**抽取后的结构化事实**（页 + 行 + 账号），不落原始正文，
  因此改口径要重跑一次平台请求（十几页，成本可接受）。
- **仍为全量重算**（ADR-0007 决策 6 未变）：按页账本的增量依然缺席。
- `data/confluence-organizations.json` 与 `data/confluence-accounts.json` 的存量数据需
  随 `schemaVersion` 一起迁移（字段改名），否则读侧会 fail-fast。

**不受影响**

- 采集器仍只写自己的数据文件，API 只读链路与 `providers.module.ts` 不变。
- GitHub 采集与其状态文件不变；`.sync-state.confluence.json` 仍独立。

## 备注

- 实测踩坑：`Requirement Proposal` 在 `Releases` 根目录下另有一张**同名模板页** ——
  只按标题匹配会多算一页，故祖先链条件是必需的而非防御性的。
- 实测踩坑：以「先按标签/关键字选页」为口径时，v3 probe 把 `Contacts` 之外的 @ 也算进过，
  58 vs 38 的差额就来自那些非联系人单元格 —— 这是"必须只取目标单元格"的直接证据。
- 08 文档 P7（Confluence 账号级候选池）本轮仍不做，但账号级文件已具备
  accountId + 展示名 + 两个维度的量，后续接入成本更低。

## 后续修订（2026-09-28，首次真实采集后）

决策 2 的取数范围经实测**放宽为「`Agenda` 段内全部 @」**，其余不变：

- **为什么改**：原口径"只取段内表格行"在真实正文上**恒 0** —— 该段只有一张布局表格，
  分享人写在「议题标题 + @分享人」的**段落**里；而"全页取"仍不可取（156 处里 125 处是出席签到）。
- **改后实测**（16 期会议）：段内原始 @ 24 处 → 按期去重 **20 次 / 12 个账号**；
  其中 4 期段内**没有任何** @（正文根本没写分享人，连纯文本 `@` 也没有），该维度因此天然稀疏。
- **同步扩展决策 7**：`Agenda` 段内写成纯文本的 `@人` 也记入 `unresolvedContacts`
  （`source: "minutes"`，行号为 `null`；首次真实采集 3 处，其中纪要段 2 处）。
- **新增第三条自检信号**：有纪要页却解析出 0 个议题分享人 → 中止写入。
  原两条（选到 0 页 / 全页无 `Agenda` 段）挡不住这次的口径失配 —— 当时两条**都是通过的**。
- **展示名实测**（**已由「后续修订之二」取代，此处保留当时的判断过程**）：正文 mention 标签只有
  `ri:account-id` / `ri:local-id` 两个属性 —— 决策 8 里"正文 `ri:username`"这一级在目标空间**永不命中**；
  `GET /rest/api/user?accountId=` 返回 **403**（令牌无读用户资料权限）。当时以为只有"被抓到过创建者页面"
  的账号有真名（15 个里 4 个），其余呈现 accountId，结论是"需给令牌补读用户资料权限"。
  **当时的举证**：需求页 `Requirement Proposal`（`pageId=1163362317`）38 处联系人 @ 覆盖 11 个账号，其中 9 个兜底为 accountId；
  纪要页有 8 期（2026-07-28 / 08-04 / 08-25 / 09-01 / 09-08 / 09-15 / 09-22 / 09-29）命中兜底账号
  —— 即"正文没有名字"与"令牌读不到资料"是同一枚硬币的两面。
- **未变**：选页口径、四条归属路径、按期去重语义、契约文件结构与 `schemaVersion`
  （`unresolvedContacts` 所在的状态文件本就非契约，加 `source` 字段无需升版）。

## 后续修订之二（2026-09-28，展示名改取渲染视图）

决策 8 的展示名来源**改以渲染视图为主**，兜底链顺序重排：

- **触发**：用户对"需求页 `Contacts` 列明明显示 `@FeiGuo`、导出数据却只有一串 accountId"提出质疑 ——
  同一份正文，浏览器里能点击、能复制出名字，采集端只能拿到 ID。
- **根因**：Confluence 的**正文**（`storage`）只存 `ri:account-id`，名字是渲染时用**查看者凭据**
  去用户目录换出来的（页面上的 mention 渲染成 `<a href="…/wiki/people/<accountId>">名字</a>`）；
  而采集令牌读用户资料恒 **403**（`/rest/api/user/current` 甚至返回 `Anonymous`），
  于是三级兜底的后两级（`ri:username` 正文里本就没有、`/rest/api/user` 被拒）**同时失效**，
  15 个账号里只剩 4 个"恰好是页面创建者"的有名字。
- **决策**：不再另请权限，也不逐账号 N+1 查资料 —— 正文请求改为
  `?expand=body.storage,body.view`，**同一请求**顺带回渲染视图，从中取
  `<a class="…user-mention" data-account-id="X" …>FeiGuo</a>` 的锚点文本：
  **渲染视图 → 正文 `ri:username` → 页面创建者展示名 → `GET /rest/api/user` → accountId**。
- **代价与边界**：每页多返回一份渲染 HTML（量级十几页，可接受）；渲染视图里 `Unknown user` 之类
  占位文本（账号停用/被删）一律跳过并继续兜底。展示名**仍不参与计数与归属**，只影响可读性
  （以及 `aliases.confluence` 的可读名匹配，与改前一致）。
- **改后实测**：15 个账号 **15 个全部取到真名**（如 `5da82cb11a43fe0ddbb47e83` = **FeiGuo**）；
  来源分档 `渲染视图 15｜正文 username 0｜创建者 0｜账号查询 0｜降级 accountId 0`，
  且**不再对 `/rest/api/user` 发任何请求**。同日复核取数：需求 38 条 · 议题分享 **21** 次
  （段内原始 @ **25** 处）/ 16 期会议；纯文本 `@人` 4 处待运营修正正文。
- **新增断言**（离线自检 67 → **70 项**）：渲染视图锚点抽取（嵌套标签取纯文本、占位与空文本跳过）
  两条单元断言 + 兜底顺序与来源分档计数断言；fixture 记录新增 `views` 字段，
  五个账号分别落在五个档位上。
- **未变**：两个维度的计数口径、四条归属路径、契约文件结构与 `schemaVersion`、API 路由与前端。
