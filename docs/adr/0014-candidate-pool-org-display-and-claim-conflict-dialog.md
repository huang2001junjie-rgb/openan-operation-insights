# ADR-0014：候选池展示组织归属 + 认领冲突弹窗

- 日期：2026-10-08
- 状态：已接受
- 决策者：项目负责人
- 关联：ADR-0008（两套归属并存）、ADR-0010（认领优先的 Confluence 生效口径）、ADR-0006（认领目标交互）

## 背景

身份匹配控制台的候选池此前只显示「已被哪个自然人认领」（`claimedBy`），不显示任何**组织归属**信息。运营在认领时无法判断「这个账号自动匹配到了哪个组织」，也无法在点击前发现「目标自然人的归属与账号的自动归属不一致」。诉求（经拷问式评审 grill-with-docs 产生，先给必要性判定，再由决策者逐条拍板）：

1. 候选池每条账号显示**属于哪个组织**（含已认领自然人的组织）；
2. 手动认领的自然人归属与自动匹配结果冲突时，**弹窗提示**。

## 决策

| # | 问题 | 决策 |
| --- | --- | --- |
| 1 | 候选行显示哪个口径的组织 | **两者都显示**：账号的采集口径归属（自动匹配结果）+ `claimedBy` 每个认领自然人的组织。生效口径（effectiveOrgId）在认领后会被人工作废，用它展示会把冲突抹掉，故不采用 |
| 2 | Confluence 侧返回口径 | **落盘采集口径** `orgId` + `orgSource`（`alias` / `space` / `unattributed`），**不是** effectiveOrgId。本场景的比对基线是「自动匹配结果」；生效口径的定义与对外展示职责不变（ADR-0010 不受影响） |
| 3 | 冲突触发边界 | 弹窗条件：`候选.orgId`（采集口径）**非空** 且 `≠ 目标 Person.orgId`。账号无采集归属（`null`）或 `meeting` 来源（例会人名与组织无关联）→ 无可比对象，**不弹**。目标自然人**未归属**（`orgId = null`）而账号有归属时**也弹**，并提供「认领并归属到该组织」快捷路径 |
| 4 | 弹窗形态 | 居中**模态确认框**（沿用 `AdminTokenDialog` 模式，Escape / 遮罩关闭），列明两边归属，按钮为 [取消] / [仅认领]（人已有归属时文案为「仍要认领」）。**提醒不阻断**（ADR-0008 决策 5），不做硬拦截 |
| 5 | 「认领并归属」的语义与顺序 | 仅在**目标自然人未归属**时出现（把一个组织的人改到另一个组织属重大调整，不给快捷路径，仍走详情抽屉）。顺序为**先认领、认领成功后再 `PATCH` 自然人归属**（复用既有 `PATCH /api/identity/persons/:personId`，无新接口）：认领被拒则不动归属，避免「归属改了但没认领」的半成品状态 |
| 6 | 冲突检测位置 | **纯前端比对**：候选接口补齐 `orgId` 后，前端已同时持有候选与选中自然人的 `orgId`，点击「认领」时本地比对即可；写接口不引入「警告码 + 确认重试」语义（与服务端「同账号被多人引用仅 WARN」的宽松口径一致）。失效代价仅为漏提醒，不产生错误数据 |
| 7 | 组织名解析 | **后端读时解析** `organizations.json` 冗余返回 `orgName`（与 `OrganizationContribution.orgName` 的冗余展示名惯例一致）；组织档案缺失 / 损坏时降级为 `orgName = null`（候选仍带 `orgId`）并在 `warnings` 中说明 |

## 理由

- **信息前置到操作现场**：认领决策最需要的线索是「该账号看起来像谁的人」。ADR-0008 已定「两套归属并存、不一致只提醒」，本 ADR 把提醒从服务端日志前移到认领动作发生前，不改变任何仲裁规则。
- **采集口径是唯一的比对基线**：`effectiveOrgId` 在认领成功后立即被人工口径覆盖（ADR-0010），若用它比对，「冲突」在认领瞬间消失，提醒失去意义；落盘 `orgId` 本就定位为「采集器看到了什么」。
- **零新写接口**：展示与冲突检测所需数据全部由既有只读接口派生字段 + 既有 `PATCH persons` 组合完成，契约变更仅为派生接口的非破坏性字段新增（不落盘，`schemaVersion` 不变）。

## 后果

**受影响面**：

- `GET /api/identity/candidates`（04 §5.3.11）：`github` / `confluence` 分组每条新增 `orgId` / `orgName`（可空），`confluence` 另带 `orgSource`；`claimedBy[]` 元素新增 `orgId` / `orgName`（认领自然人的归属，`Person.orgId` 读时 join）。
- 前端：`ClaimRow` 展示账号采集归属徽标与认领人组织；新增 `OrgConflictDialog` 模态；`IdentityConsolePage.handleClaim` 认领前比对，命中冲突先弹窗。
- **不变**：所有落盘文件与 `schemaVersion`；`POST /api/identity/claims` 入参与语义；GitHub 双轨、Confluence 认领优先的既有口径；`meeting` 候选无组织字段。

**正面**：

- 认领前的归属冲突可视、可一键对齐（「认领并归属」），减少事后在详情抽屉补救；
- 冲突检测为纯展示层关怀，服务端写路径保持「持久化 + 审计」单一职责。

**代价 / 风险**：

- 前端比对依赖候选缓存新鲜度，极端情况下**漏提醒**（不阻断、不产生错误数据，可接受）；
- `github-accounts.json` 的 `orgId` 可能是人工指定值（采集器不覆盖人工值），弹窗不区分其来源，文案统一称「自动匹配归属」——属可接受的表述简化。
