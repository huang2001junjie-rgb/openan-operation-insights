# ADR-0005：例会参会情况采用无主键二维矩阵，空白计为缺席

> **后续修订（2026-11-10）**：决策 5 的「前端不可重排」收窄为「**列序**不可重排」——**行序**（日期）改为前端渲染时**最新例会在上**（接口与落盘仍保持台账原序，仅 `MeetingAttendanceMatrix` 渲染时反转）。运营确认：出勤场景读者最关心最近一场。其余决策（无主键、空白 = 缺席、纯透传、放弃元信息）不变。见 README §9 v1.37。

- **状态**：已接受
- **日期**：2026-09-23
- **关联文档**：04 §3.8/4.7/5.3.9、02 §6、03 §4.5、05 §10；修订 01 的页面清单与风险表

## 背景

运营团队需要一个长期缺失的视图：**谁在坚持参加社区例会**。此前的四个页面里，峰会（`/summits`）记录的是"办了哪些会、在哪办"，活跃度（`/activity`）记录的是代码贡献，没有任何地方回答"例会的出勤情况如何"。

约束条件来自运营侧的真实工作方式：

1. 例会台账**已经存在**，是一张在 Excel 里手工维护的二维表——第 1 行是日期，其后每行是一位成员，格子里的记号表示是否出席。
2. 台账**没有主键、没有成员档案、没有会议元信息**（时长、主持人、议程一概没有，也不打算记录）。
3. 数据规模很小：数十场例会 × 数十人。
4. 出席信息**可以公开**到个人明细粒度。
5. 短期目标是"先把现有表格搬上来"，**不是**先建一套规范化的考勤模型再接 Zoom。

若沿用既有实体（组织 / 贡献者 / 峰会）去建模，会因为"例会成员 ≠ GitHub 贡献者"而产生大量无意义的映射与主键设计，与运营的实际维护方式背道而驰。

## 决策

1. **独立新实体 `Meeting`**：与峰会、组织、贡献者**完全解耦**，不改动任何既有实体；新增 `data/meetings.json` 与 `GET /api/meetings`。
2. **照搬 Excel 台账**：`data/meetings.json` 直接落成**二维矩阵**——行 = 日期、列 = 人名（照搬表头的**原序与原文**），格 = `boolean`。**不设主键、不做规范化、不做聚合**。
3. **有记录即算出席**：出席是**二值**判定（`true` = 出席，`false` = 缺席），不区分迟到 / 早退 / 请假。
4. **空白 = 缺席**：台账中未标记的格子一律解析为 `false`，并**计入出席率的分母**。
5. **前端不可重排**：矩阵严格保留台账原序（行序与列序皆不可在前端重排），页面只做展示。
6. **完全放弃会议元信息**：不记录时长、主持人、议程、地点、纪要。
7. **采集走脚本，且是读写分离的一环**：运营继续手工维护 `data/source/meetings.xlsx`，由 `apps/api/scripts/import-meetings.ts`（Node + `exceljs`，`npm run collect:meetings`）转换为 `data/meetings.json`；接口侧 `MeetingAttendancePort` **恒为 JSON 读实现、纯透传**。
8. **删除首页与峰会页的"例会"字样**：避免与例会页形成双重口径。

## 理由与取舍

| 选项 | 结论 |
| --- | --- |
| 建模方式：规范化考勤实体（成员表 + 场次表 + 出席表）/ 照搬二维矩阵 | **照搬矩阵**。运营的维护表面就是矩阵，矩阵也是问题的最小充分表示；规范化会引入主键、成员映射与聚合视图，收益率极低 |
| 与峰会的关系：复用 `Summit` / 独立实体 | **独立实体**。例会成员与峰会参与者、GitHub 贡献者是不同人群，强行关联只会制造维护负担 |
| 出席粒度：二值 / 三态（迟到 / 请假）/ 计时长 | **二值**。台账只有"来没来"，其余信息本就不存在，任何更细的粒度都是凭空造数据 |
| 空白语义：未知 / 缺席 | **缺席**。运营明确要求"空白就是没来"，且出席率需要确定的分母 |
| 序号维护：前端可排序 / 锁死原序 | **锁死原序**。矩阵的"人 × 日期"位置本身即上下文，重排会破坏与 Excel 台账的对照关系 |
| 会议元信息：采集 / 放弃 | **放弃**。运营明确表示不需要，采集它们需要额外的人工录入成本 |
| 数据接入：先手动维护 JSON / 立即接 Zoom API | **先 Excel 台账 + 转换脚本，Zoom API 列为远期**。当前没有 Zoom 侧的成员映射与 API 权限，先跑通"台账 → JSON → 接口 → 页面"的完整链路 |
| 出席记号：固定白名单 / 宽容匹配 | **宽容匹配兜底**（`√`/`✓`/`Y`/`y`/`1`/`是`/`x`/`X`/`出席` → `true`），拿到真实台账后按实际记号校准（05 §10.4 待办） |

## 后果

**正面**

- 以最小成本补齐了"例会出勤"这一长期空白；数据链路完整（Excel → 脚本 → JSON → 接口 → 页面），后续接 Zoom 时只替换脚本，**契约与页面零改动**。
- 契约层保持极简：一个实体、一个无参接口、无聚合、无关联，前后端实现成本都很低；`MeetingAttendancePort` 是纯透传，无需 DTO 与业务逻辑。
- 与既有架构一致：仍遵守"采集写、接口读"的读写分离，端口恒为 JSON 实现。

**负面（明知并接受的负债）**

- **无主键 → 接 Zoom 时需重建映射**：列名即人名、无任何稳定标识，人名重名、改名、空格差异都会产生重复列或断裂列。将来接 Zoom API 时，必须先建立"Zoom 参会者 ↔ 台账列名"的映射，届时可能需要一次性的人工核对。
- **空白 = 缺席 → 会系统性冤枉后加入的成员**：成员加入之前的历史格子是空的，会被计入缺席，导致其出席率被历史空白拉低，**不能跨成员横向比较**。这是本决策的核心代价，运营**已知悉并明确接受**；页面必须以常驻口径说明向读者提示这一点（见 02 §6.3）。
- **不可重排 → 排序类需求需另找出口**：用户无法按出席率 / 姓名重新排列矩阵。为缓解矛盾，个人出席率挂**列头副标签**、每场出席人数挂**行头**（见 02 §6）。
- **放弃元信息 → 不可回溯会议内容**：无法回答"哪场会讲了什么、谁主持"，若未来有此需求需另立实体。
- **删除"例会"字样 → 既有页面文案调整**：首页与峰会页原有的"例会"提及被移除，属于对既有描述的修订。

**不受影响**

- 所有既有实体（组织 / 贡献 / 洞察 / 贡献者 / 峰会）、既有接口、既有页面逻辑均不受影响；例会数据与它们是并列的第七个数据文件。
- GitHub / Confluence 采集链路不受影响。

## 备注

- 源台账 `data/source/meetings.xlsx` **不是契约文件**，仅是采集器的输入，其列名 / 记号可被运营自由调整（详见 05 §1.2 约束 5）。
- 个人出席率（`present / rows.length`）与每场出席人数均由**前端派生**，接口不返回聚合字段（04 §3.8）。
